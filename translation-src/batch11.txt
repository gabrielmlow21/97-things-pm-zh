# 保持弹性，让项目管理更简单
17 世纪有名的武士宫本武藏相信这样一个原则：“不要偏爱任何一种武器，也不要执着于任何一种流派。”这个建议在我们的项目生活中也很适用。我们千万不能太依赖某一种管理原则、软件工具或编程语言，把它当成唯一的武器。只有用灵活的方式看待手上的资源，让它们可以按很多不同的方式组合，我们才能为那些变成项目的客户问题，准备好最好的应对方法。

从定义项目需求的一开始，就要保持开放的心态。如果你还没和客户谈，就已经选好武器和作战计划，你怎么能确定你事先定好的方案就是最好的？

选武器之前，先看清楚客户所有的需求。客户想用你的新软件解决什么问题？这些问题通常和某些业务逻辑有关，说明现有的资源功能不够多、不够强。接着，看看公司里现有的各种条件和系统。巧妙地重用现有系统的一部分，能让项目的路更短、更好走。

可以用的企业环境条件包括很多不同的东西，比如公司现有的设施、设备和软件，商业和自有的数据库，编程工具，以及员工的技能。

针对软件或其他项目交付物要满足的客户需求，做一次以资源为主的分析，会发现一些公司里早就存在的资源。“我们的用户必须能把 XPP34 <b>客服中心系统</b>和我们的<b>公司应收账款系统</b>并排着看。”“你们的产品必须和我们的 4465IL <b>旧系统</b>合并，或者兼容。”

你的工作是问对问题：客户期待的各种最终表现是什么，以及现有的资源/软件或系统要怎样和你的新代码配合。用这种以资源为主的方法，你也许能为客户以后会想要的改变打好基础。分析完后，你的软件就开始成形为一组新的资源：它们不只能解决今天的问题，也能用来完成以后的项目，并和未来的软件互动。

等你知道客户想要什么，也知道公司里有哪些必须考虑的现有资源，“这时”你才能选出对付这个问题最好的武器。实际开发可以先集中在几个关键需求上，先交出来，赢得客户的信任。满足关键需求所需的模块和服务应该先做。

在软件设计上对新路线保持开放，能让你在需求不断变化的世界里，用一种轻松的方式处理软件项目。这种弹性会让你的项目管理挑战变得更简单，而不断打造新的武器和计划，也会让你每天的工作有趣又充实。

=== The_Web_Points_the_Way_For_Now.htm
# Web 指出了方向——至少现在是这样
有一个慈善团体的口号是：“我们站在前人的肩膀上。我们为后来的人提供肩膀。”这句话对我们这些软件开发人员很有意义。每当一种新的架构、语言或平台流行起来，我们常常会感叹：“这就是解决所有编程问题的答案。”它也许能解决今天的问题，但明天还会有新的挑战。

目前，我们只知道刚好一种软件架构，能扩展到几十亿用户，同时在个别组件出问题时依然很稳健*：那就是万维网。到目前为止，Web 是人类建造过的最大、使用最多、最稳健的信息检索系统。

为什么 Web 运作得这么好？鼎鼎大名的 Apache** 项目创办人之一罗伊·菲尔丁（Roy Fielding）研究的正是这个问题。菲尔丁分析了早期 Web 的一个理想化版本的架构，从中整理出了架构风格的要素。

结果就是一种新的软件架构风格，拥有我们喜爱的 Web 的那些特点：它们在面对变化和个别组件故障时都很稳健；它们把关注的事情分开，让我们不必再管编程语言这类实现细节；它们用一种共同的“通用语”（让母语不同的人能互相沟通的语言）来交换和语言无关的信息请求；它们非常容易扩展；它们是无状态的。

不是每个网站都用了这些原则，但很多网站都用了，而 Web 整体也用了。不过，这些只是肩膀，新的创新架构会在这之上继续发展。

我们可以从 Web 的成功中学到一些重要的东西。也许最重要的是，摩尔定律***让我们现在在系统设计中可以接受大量的抽象。我们不必再对硬件和软件斤斤计较地追求效率，而是可以考虑让系统极度稳定、极度稳健、极度容易扩展、极度灵活。我们也可以接受现在架构的低效率，因为我们很清楚，它们只是未来创新的基础。

像 Web 这样的分布式系统很难设计。也许是因为我们每个人都是独立的个体。我们把软件系统当成某个人做出来的东西，就像我们每个人都以自己为中心看世界一样。不过，Web 的分布式系统已经为我们指出了方向。分布式系统比较难想清楚，所以也比较难做，但值得花力气去做。

当然，技术会变，想法和方法也会变。菲尔丁描述的那个简单的 Web，不是现在的 Web，也不会是未来的 Web。Web 不一定永远都能指出方向。适应新系统的关键，是现在就把弹性设计进我们的系统里。只有这样，我们才能开始做出有生命力、会呼吸、能适应的软件系统，随时准备好和新的发现结合，为后来的人提供肩膀。

- 稳健（Robust）——能好好应对各种变化（有时是没办法预测的变化），功能的损坏、改变或损失都降到最低。
- Apache 项目——一个开源项目，为现代操作系统开发和维护免费的 Web 服务器软件。
- 摩尔定律（Moore's Law）——描述电脑硬件长期趋势的定律：能便宜地放进集成电路的晶体管数量，以指数速度增长。

=== Who_is_my_customer.htm
# 开发人员讨厌进度报告，经理们却爱它
我在全世界最大的软件公司工作，可以作证：开发人员讨厌进度报告。它让他们每周花好几个小时，写下一些在他们看来很明显、很多余的信息。

可是对你这个软件项目经理来说，这些数据能让你更全面地了解项目进度，然后再报给高层。平均来说，一位项目经理同时管五到七个项目。你和你的高层团队，都需要你收集并传递这些项目数据。

下面是一些小技巧，能让开发人员不那么抗拒交那份“按你需要的频率”交的进度报告：

- 帮他们明白，为什么这份报告对其他团队成员，或其他要根据团队进度做计划的部门很重要。人会为了帮同伴而更努力。
- 如果项目进度慢，要知道团队在做什么。他们在学新的工具或语言吗？这周有没有遇到意想不到的问题和挑战？汇总进度报告时，加上说明，帮别人看懂这些数字。
- 给予适当的肯定。如果你知道遇到了哪些问题和挑战，就能确保任何重要的成就都不会被进度报告的数字盖住。对那些做出有帮助、计划外贡献的人，送一张附近咖啡店的拿铁券。试试发一封给整个部门的“干得好，谢谢你，&lt;名字&gt;”邮件。把这项工作和它在“大局”中的重要性直接连起来。
- 如果你管的开发人员不止一个，就设一个团体奖励。“如果连续一个月，每周五下午 3 点前我都收到你们每个人的进度报告，下个周五下午大家都放假。”或者，“我会带吃的来请大家吃一顿午餐。”没人想当那个害团队拿不到奖励的人。
- 让报告容易写。提供一个模板，或者一个交进度的电子工具。准备好把里面的用词改写成每个人都看得懂的说法。你的副总裁很可能看不懂“lcl check-in to main build lab”（本地提交到主构建实验室），你可以改成“功能里程碑 2 已达成；项目进度正常”。

重点是，一定要从对方的角度来看“定期交进度报告”这件事。进度报告很重要。每个人都需要知道发生了什么事。高层关心里程碑，业务管理层关心预算。作为项目经理，你的工作是确保每位相关方都了解项目的情况——但也要明白，不是每个相关方都能在没有你帮忙的情况下，完全看懂正在发生的所有技术细节。

找一个好用的输入工具，并尽量了解背后的工作内容。你就是那座桥梁，要写出一份能满足所有相关方需要的完整进度报告。

=== You_Are_Not_In_Control.htm
# 你并没有掌控一切
我记得我带过的一个项目团队。那位项目经理显然很想当控制的中心。他几乎像着了迷一样，需要参与所有“关键”的决策讨论。他会主动主持每天的站会，在项目回顾会上，也只由他一个人决定谁可以发言。我到的时候，他管的这个团队其实已经磨合得很好了，我很有兴趣地注意到，项目经理在场和不在场时，讨论的质量有什么不同。

我和团队里几个人一对一聊过，他们坦白说，他们讨厌项目经理开的所有会，因为他们只想快点开完。他们觉得自己的时间被浪费了，因为他们真正的意见没被重视。他们说，自己会讲一些项目经理想听的话，好让他赶快进入下一个议题。当他们有问题需要解决时，他们会去找技术负责人。他比较愿意参与开放的讨论，所以解决问题也更有效。

我从这个团队学到的是：表现得好像你在掌控局面，和真正掌控局面，不是同一件事。事实上，太积极地想掌控，有时反而会有相反的效果。一个经验丰富、磨合良好的团队，会主动避开一个为了自己而想掌控一切的人，特别是当这种掌控对团队没什么好处的时候。

项目经理了解团队互动和不同的领导风格，会很有帮助。不同的项目、不同的团队，需要不同程度的掌控。像我上面说的那种磨合良好、表现很好的团队，除非看得出过多的掌控对他们有什么帮助，否则常常会反感。

这种掌控常被看成“乱插手”，虽然团队嘴上可能同意，但他们离开会议室后的行动，可能不完全是你想要的。不过，对一个新组成的团队来说，多一点掌控可能会给团队方向，并为项目定出更清楚的目标。

很棒的项目经理会施加刚刚好的掌控，尊重团队成员为这个项目带来的技能、经验和人脉。他们看得出什么时候多一点掌控能帮团队走向最终目标，也看得出什么时候同样的掌控会拖慢团队。

当一位非 IT 背景的项目经理被要求带一个软件开发项目时，这一点尤其重要。团队常常不喜欢外人干涉他们的工作，可能会看轻项目经理为项目带来的能力。

但是，项目经理的组织能力、让项目符合公司目标的能力，以及成功维持高层和客户之间沟通渠道的能力，都能保护 IT 团队，让他们可以自由地工作。

=== Share_the_Vision.htm
# 分享愿景
你是在和一群笨蛋一起工作吗？你的团队成员想让公司破产吗？有时候感觉是这样，但通常并不是。事实是，每个人都想成功，也想为自己的贡献感到骄傲，不管他们看起来多像是在破坏你的项目。他们在做自己认为对的事，但每个人对“对”的理解都不一样。

作为软件项目经理，你怎样让大家一起合作？要知道，大多数团队都是在黑暗中工作的。他们不知道这个项目为什么重要，它在公司更大的策略里扮演什么角色，也不知道为什么截止日期是 6 月 17 日。因为不明白为什么会做某些决定，这些选择看起来就很随便、不合理。每个人都很辛苦，想在没有任何确切信息的情况下，看清这个模糊的局面。每个人看到的项目终点都不一样，我们还应该觉得奇怪吗？

要让雾散开，你需要和团队分享那些能让他们了解你们共同目标的关键信息。让他们知道，项目要在 6 月中推出，才能比竞争对手的产品早三周上市。帮他们明白，这个项目是为了配合公司更大的海外扩张策略，或者你的客户正靠它来挽救现有、但越来越老旧的产品线不断下滑的利润。

如果你刚开始学着分享信息，要小心。作为团队的信息来源，你也在影响团队的士气。当你决定抱怨另一个小组、另一位经理，或者团队里的某个人时，你的负面态度会像流感一样很快传遍整个团队。而且就像病毒感染一样，它可能让团队好几天都提不起劲。

分享项目信息的一个好方法，是每天开一次会。10 人左右的团队，只要 10 到 20 分钟就能有效地开完。每个人有一到两分钟，向团队报告自己的最新进度，需要时请大家帮忙。这种快速的“站会”，正是软件项目经理分享项目最新消息的好地方。

如果你选择每周（或每月）开一次会，你可能会忘了重要的信息。毕竟，等大家终于聚在一起时，这些对你来说已经是旧消息了。或者，一个本来可以避免的问题，因为你拖着不分享风险信号而爆发了。也许在你把 17 条“非常重要”的信息全塞进一次又长又臃肿的团队讲话后，大家早就听得两眼发直了。

记住，你的团队，以及公司里的每个人，都想成功。分享你的愿景，也请别人分享他们的。你会发现，那些你以为一心要让公司关门的笨蛋，大多数其实是会和你并肩合作、一起解决大家都明白的团队挑战的人。

=== True_Sucess_Comes_With_A_Supporting_Organization.htm
# 真正的成功，来自一个支持你的公司
如果一家公司回避风险规划、不主动找问题、也不及时解决问题，原因可能出在文化上。项目团队里那些故意唱反调的人，常常被贴上“麻烦制造者”的标签。如果公司一有坏消息就“怪罪报信的人”，团队成员就会避免说出棘手的问题，也可能倾向于把项目问题藏起来。

这种文化会鼓励互相推卸责任，伤害整个公司、员工个人和客户。软件项目经理的角色，是让项目交付可以预测，尽量少出意外。如果没有人早点指出陷阱，常常就会出现“惊喜”。这些很少是好的惊喜；通常是很糟的那种，说明因为开发人员把问题藏起来，根本不可能事先看见、事先规划。

聪明的高层会确保公司支持那些能让开发人员发挥效率的态度和行为。这包括检查人事政策和奖励制度，确保它们和能做出好产品、好服务的行为一致。

一个典型的不一致的例子是：公司官方“宣扬”团队合作，却总是奖励个人表现。大家都很聪明，知道哪条路对自己最有利。如果高层能让自己说相信的东西，和为了鼓励好行为而提供的工作环境一致，个人和公司都能发展得很好。

如果你发现自己身在一个不支持你、或运作不良的公司，下面是一些你可以做的事：

1. 一直问，直到你弄懂项目的范围，这样你才能在范围内工作。
2. 找出可能的团队成员和其他相关方。只要可以，就让他们参与脑力激荡、规划和项目执行。
3. 让真正在做事的人充分参与项目的更新和决定，至少在他们完成这个项目的工作之前都要这样。
4. 永远做一个诚实的软件项目经理。不要为了避开冲突或尴尬的讨论，就把问题掩盖或简化。
5. 在你的项目团队里，营造你希望整个公司都能拥有的环境。

项目经理必须客观地看待项目。他们处在一个吃力不讨好的位置：首先要忠于付他们薪水的公司，同时又要和开发人员建立信任。如果项目前景很糟，一个精明、有原则的项目经理应该建议先取消项目，等周边的问题解决了再说。

我们都希望在一家有一致策略、支持新软件项目开发的公司工作。但可惜的是，就算在同一家公司的不同部门之间，这种能力也可能差很多。因为朝更支持员工的环境前进对每个人都有好处，提醒高层注意项目优先顺序和绩效奖励之间的文化冲突，应该成为软件项目经理工作的一部分。

=== Establish_Project_Management_Governance.htm
# 建立项目管理的治理机制
一个项目可能要和很多人打交道，包括团队成员、供应商团队成员、客户或项目发起人、运营团队、合同团队、财务团队，以及其他相关方。在这种牵涉很多人的情况下，各种状况都可能危及项目。

如果你是 IT 背景出身的软件项目经理，了解怎样融入你部门以外更大范围的项目管理，可能会对你有帮助。

治理（governance）是一种管理方法，用来制定、传达、执行和监控运作项目所需的政策、程序、做法和其他行动。建立有效的项目治理结构和程序，有助于确保项目方向一致、监控威胁和机会、做决定，以及交出专注于原定计划的项目工作包。它让你能适当地处理风险，从而满足项目需求。

要有效，项目治理应该事先规划。在它的框架里处理相关的事项，例如：治理的目标；结构；原则；流程、程序和标准；沟通；汇报关系；上报程序（什么事、什么时候、怎么报、由谁报）；工具；定义清楚并确实执行的职责和责任；衡量方式和标准；质量；会议和指导委员会；审核；以及监控。

要记住，治理可能会受到很多因素影响：环境、领域、行业、公司文化和法律规定。比如，在职能型组织里，作为项目经理的你可能直接向部门经理汇报，而不是向项目组合经理或项目群经理汇报。在项目型组织里，所有工作都以项目的方式进行，项目经理的权力最大。但在职能型组织里，你可能直接向直属主管或部门经理汇报，权力实际上就被削弱了。

所以，在规划和定义治理架构时，要考虑公司的层级结构。可以按照工作的发展和进度，视需要修改这个结构，让项目一直符合原定的目标。在大项目里，要让你的工作配合更大的项目群或项目组合的目标。但就算你管的是很小的项目，也要建立或调整一个项目治理模式。

通常，项目管理办公室（PMO）负责定义和管理项目相关的程序、流程，并制作应该遵守的模板。

项目委员会是一个负责确保项目目标达成的组织。它支持适当地处理项目风险和其他问题。委员会有下面这些作用：

- 批准项目计划和计划的变更；
- 收集用来报告进度的信息；
- 确保遵守政策、程序、标准和要求；
- 对风险和问题提供指导；
- 检查项目进度。

当项目和其他公司打交道时，项目治理应该和其他组织的治理结构整合起来运作。

# 我讨厌你的网站的 9.7 个理由
大多数公司不知道软件开发和网站开发不一样，所以软件项目经理和软件开发人员会被叫去做网站。下面是 9.7 种方法，能让你那个烦人的网站使我永远不和你的公司做生意。

1. <b>一开始就放一个加载很慢的 Flash 画面。</b>不让我跳过，然后每个页面刷新时都继续让我等个没完。你竞争对手的快速反应正在召唤我。
2. <b>用吓人、震耳欲聋的影片给我“惊喜”。</b>我可能在上班，可能在家、旁边有睡着的孩子或另一半，也可能正在偷偷买礼物。如果你真的想把我赶走，那就别放关闭按钮。
3. <b>让“返回”按钮失效。</b>你不让我回到带我来你网站的搜索引擎，觉得自己很聪明，但我不会被困第二次。下次，我不会再点你的网页，也不会买你卖的任何产品或服务。
4. <b>选一套很难看清楚的配色。</b>在稍微深一点的灰色背景上用灰色字，也许很特别，但根本看不清。鼠标一点，就有 25 个别的网站可以让我不用看到眼瞎就能读到信息。另外，用反白的字又不让我轻松复制粘贴，代表我没办法保存你的资料，留着以后决定要不要买。
5. <b>不管我的随身设备。</b>我可能带着 iPhone、Kindle 或上网本。如果你没有一个快速、轻量的手机版界面，你就不是我需要的现代化公司。我们正在离开客户端/服务器模式，回到老式的“哑终端”，连着天上某台强大的电脑。为此做好准备吧。
6. <b>不给我任何能打电话找到真人的方法。</b>如果我遇到问题，在我已经用尽了你们网站支持功能那点有限的帮助后，还坚持要我继续用它，这根本不对。我要去找你的竞争对手了。难道你不想知道你的网站什么时候坏了吗？
7. <b>坚持要我打电话才能拿到信息。</b>除非你卖的是从来没人做过的产品，比如传送到土星，不然你一定知道自己的价格。给我看。竞争对手可以假装客户打电话来问到价格。而你却失去了我这个真正的客户。
8. <b>对不同类型的客户差别待遇。</b>如果我是公司，就能拿到比较旧的操作系统，那我不应该只因为自己是个人，就被迫升级到一个不稳定的系统。如果我在航空公司网站上查往返航班，那么当我想一段一段地选多城市航班时，也应该看到所有相同的航班。
9. <b>放一个没用的搜索功能。</b>我想搜的是你网站的内容，而不只是和我要找的主题有关的公关新闻稿。

9.7 <b>把按钮标错。</b>如果“阅读更多”按钮把我带到一段影片，我会很生气。我想快速浏览你的文字信息，而不是坐着看完一整段简报。

<b>别让我讨厌你！</b>
