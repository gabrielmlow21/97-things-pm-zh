=== RESTful_Architecture_Makes_Project_Management_Extremely_Simple.htm
# 灵活性让项目管理更简单
17 世纪著名的武士宫本武藏信奉这样一条原则：“不要偏爱任何一种兵器，也不要拘泥于任何一个流派。”这条建议在我们的项目生涯中同样适用。我们决不能过于依恋某一种管理原则、软件工具或编程语言，把它当作我们唯一的武器。只有以灵活的方式看待我们的资源，让它们可以按多种不同的配置进行组合，我们才能为那些成为我们项目的客户问题准备好最佳的应对方案。

从定义项目需求的那一刻起，就要采取一种开放的态度。如果你在和客户交谈之前就已经选好了武器和作战计划，你怎么能确定你预先定义的解决方案就是最好的呢？

在挑选武器之前，先审视客户的所有需求。客户想用你的新软件解决什么问题？这些问题通常与某种业务逻辑有关，表明现有的资源在特性或功能上不够丰富。接下来，考虑组织内现有的各种因素和系统。巧妙地重用现有环境系统中的部分组件，可以缩短并简化你的项目之路。

可用的企业环境因素包括各种各样的东西，比如公司现有设施、设备和软件的基础设施，商业和私有数据库，编程工具，以及人力资源技能。

对软件或其他项目可交付成果需要满足的客户需求进行以资源为导向的分析，会揭示出组织中已经存在的一些底层资源。“我们的用户必须能把 XPP34 <b>呼叫中心系统</b>和我们的<b>企业应收账款系统</b>并排查看。”“你们的产品需要与我们的 4465IL <b>遗留软件</b>合并，或者与之兼容。”

你的工作是就客户期望的各种最终性能结果，以及现有资源/软件或系统如何与你的新代码输出相互关联，提出正确的问题。运用这种以资源为导向的方法，你也许能为客户将来想要的变更打下基础。在这一分析结束时，你的软件开始成形为一组新的资源：它们不仅能解决今天的问题，还能用于完成今后的项目，并与未来的软件交互。

一旦你知道了客户想要什么，也知道了组织中有哪些必须考虑在内的现有资源，“现在”你才可以选择对付这个问题的最佳武器。实际的开发可以首先集中在少数几项关键需求上，通过交付它们来赢得客户的信任。满足关键需求所需的模块和服务应该首先实现。

在软件设计中对新的路径保持开放的心态，为在需求不断变化的世界中处理软件项目提供了一种愉快的方式。这种灵活性将简化你在项目管理中面临的挑战，而打造新的武器和计划，也会让你的工作日充满趣味、收获满满。

=== The_Web_Points_the_Way_For_Now.htm
# Web 指明了方向——至少目前如此
有一个慈善团体的口号是：“我们站在前人的肩膀上。我们为后来者提供肩膀。”这句话对我们这些软件开发人员很有意义。每当一种新的架构、语言或平台崭露头角，我们往往会感叹：“这就是解决我们所有编程问题的答案。”它也许能解决今天的问题，但明天我们又会面临新的挑战。

目前，我们只知道恰好一种软件架构，既能扩展到数十亿用户，又能在单个组件出现故障时保持健壮*：那就是万维网。Web 是人类迄今为止构建的规模最大、使用最多、最健壮的信息检索系统。

Web 为什么运行得这么好？著名的 Apache** 项目创始人之一罗伊·菲尔丁（Roy Fielding）研究的正是这个问题。菲尔丁评估了早期 Web 的一个理想化版本的架构，并从中提炼出了架构风格的要素。

其结果是一种新的软件架构风格，具备我们所喜爱的 Web 的那些特性：它们对变化和特定组件的故障都很健壮；它们实现了关注点分离，让我们不必再关心编程语言之类的实现细节；它们使用一种共同的“通用语”（一种在没有共同母语的人之间进行交流的语言）来交换与语言无关的信息请求；它们的可扩展性极强；它们是无状态的。

并非每个网站都使用这些指导原则，但许多网站都在使用，而且 Web 作为一个整体也在使用它们。然而，这些只是肩膀，新的创新架构将在此之上持续发展。

我们可以从 Web 的成功中学到一些重要的东西。也许最重要的一点是，摩尔定律***如今允许我们在系统设计中接受大量的抽象。我们不必再对硬件和软件精打细算地追求效率，而是可以考虑让系统极度稳定、极度健壮、极度可扩展、极度灵活。我们也可以接受当前架构的低效之处，因为我们非常清楚，它们只是未来创新的基础。

像 Web 这样的分布式系统很难设计。也许这是因为我们每个人都是个体。我们把软件系统看作由某个个体创造的东西，就像我们每个人都以自我为中心看世界一样。不过，Web 的分布式系统已经为我们指明了方向。分布式系统更难构想，因而也更难创建，但创建它们是值得的。

当然，技术会变化，理念和技术手段也会变化。菲尔丁所描述的简单的 Web 并不是现代的 Web，也不会是未来的 Web。Web 未必永远都能指明方向。适应新系统的关键，在于现在就把灵活性设计到我们的系统中。只有这样，我们才能开始创造有生命力、会呼吸、能适应的软件系统，随时准备与新的发现相融合，为后来者提供肩膀。

- 健壮（Robust）——能够很好地应对各种变化（有时是不可预测的变化），而功能的损害、改变或丧失降到最低。
- Apache 项目——一个开源项目，为现代操作系统开发和维护免费的 Web 服务器软件。
- 摩尔定律（Moore's Law）——描述计算机硬件长期趋势的定律：可以低成本地放置在集成电路上的晶体管数量呈指数级增长。

=== Who_is_my_customer.htm
# 开发人员讨厌状态报告，经理们却爱它
我在世界上最大的软件公司工作，可以证明开发人员讨厌状态报告。它让他们每周要花好几个小时，写下那些在他们看来显而易见、多余的信息。

然而，对于身为软件项目经理的你来说，这些数据可以用来更全面地了解项目进展，然后再上报给高层管理者。平均而言，一位项目经理同时掌管五到七个项目。你和你的高层管理团队都需要你收集并传递这些项目数据。

下面是一些技巧，可以让开发人员不那么抗拒提交他们那份“按你需要的频率”提交的状态报告：

- 帮助他们理解，为什么这份报告对其他团队成员或其他需要根据团队进展做计划的部门很重要。人们会为了帮助同伴而更加努力。
- 如果项目进展缓慢，要了解团队在做什么。他们是在学习新的工具或语言吗？这周是否遇到了意想不到的问题和挑战？在汇总状态报告时，加上解释性的信息，帮助其他人理解这些数字。
- 给予恰当的认可。如果你知道遇到了哪些问题和挑战，就能确保任何重大成就都不会被进展报告的指标所掩盖。对于那些做出了有益的、计划外贡献的人，送一张附近咖啡店的拿铁券。试试发一封抄送整个事业部的“干得好，谢谢你，&lt;姓名&gt;”的邮件。把这项工作与它在“全局”中的重要性直接联系起来。
- 如果你管理的开发人员不止一个，就设立一个集体奖励。“如果连续一个月，每周五下午 3 点前我都能收到你们所有人的状态报告，那么下个周五下午大家都放假。”或者，“我会带吃的来请大家吃顿午餐。”没有人愿意成为那个让团队拿不到奖励的人。
- 让报告容易写。提供一个模板或一个提交状态的电子工具。做好准备，把其中的措辞改写成每个人都能理解的样子。你的副总裁很可能看不懂“lcl check-in to main build lab”（本地签入主构建实验室），你可以把它改成“功能里程碑 2 已达成；项目进展正常”。

关键在于，一定要从对方的角度来看待完成定期状态报告这项任务。状态报告很重要。每个人都需要知道正在发生什么。高层管理者关心里程碑，业务管理者关心预算。作为项目经理，你的工作是确保每位干系人都了解项目的情况——同时也要认识到，并非所有干系人都能在没有你帮助的情况下，充分分析正在发生的事情中的所有技术细节。

找到一个有效的输入工具，并努力尽可能多地了解背后的任务。你是联络人，要编写出一份能满足所有干系人需要的全面的状态报告。

=== You_Are_Not_In_Control.htm
# 你并不掌控一切
我记得我指导过的一个项目团队。项目经理显然很想成为控制的中心。他似乎近乎执念般地需要参与所有“关键”的决策讨论。他会积极地主持每日站会，在项目回顾仪式上，也由他一个人决定谁可以发言。我到那里的时候，他管理的这个团队其实已经磨合得很好了，我饶有兴趣地注意到，项目经理在场和不在场时，讨论的质量有什么不同。

我和团队中的几个人一对一地交谈，他们坦白说，他们讨厌项目经理召开的所有会议，因为他们只盼着会议早点结束。他们觉得自己的时间被浪费了，因为他们真实的意见得不到重视。他们讲述了自己是如何说一些项目经理想听的话，好让他赶紧进入下一个议题。当他们有需要解决的问题时，他们会去找技术负责人。他更愿意参与开放的讨论，因此在解决问题方面也更有成效。

我从这个团队身上学到的教训是：表现得好像你掌控着局面，和真正掌控局面并不是一回事。事实上，积极地寻求控制有时反而会产生相反的效果。一个经验丰富、磨合良好的团队，会主动回避一个出于个人原因试图掌控局面的人，尤其是当这种控制对团队几乎没有好处的时候。

项目经理了解群体动力学和不同的领导风格是有帮助的。不同的项目和不同的团队需要不同程度的控制。像我上面提到的那种磨合良好、高绩效的团队，除非能看到过多的控制对他们有什么帮助，否则往往会对此心生反感。

这种控制常常会被视为“瞎掺和”，虽然团队口头上可能会同意，但他们离开会议室后的行动可能并不能完全体现你的本意。然而，对于一个新组建的团队来说，更多的控制可能会为团队提供方向，并为项目确立更清晰的目标。

伟大的项目经理会施加恰到好处的控制，尊重团队成员为手头项目带来的技能、经验和人脉。他们能识别出更多的控制可能有助于推动团队实现最终目标的迹象，也能识别出同样的控制可能正在拖慢团队的迹象。

当一位非 IT 背景的项目经理被要求领导一个软件开发项目时，这一点就更为关键了。团队往往会反感外人干涉他们的工作领域，可能会低估项目经理为项目带来的技能。

但是，项目经理的组织能力、让项目与公司目标保持一致的能力，以及成功维护高层管理者与客户之间沟通渠道的能力，都可以保护 IT 团队，让他们能自由地工作。

=== Share_the_Vision.htm
# 分享愿景
你是在和一群白痴共事吗？你的团队成员想让公司破产吗？有时候感觉是这样，但通常并非如此。事实是，每个人都希望成功，并为自己的贡献感到自豪，无论他们看起来多么像是在试图破坏你的项目。他们在做自己认为正确的事情，但每个人对“正确”都有自己的理解。

作为软件项目经理，你如何让每个人齐心协力？要知道，大多数团队都是在黑暗中劳作的。他们不知道这个项目为什么重要，它如何融入公司更宏大的战略，也不知道为什么截止日期是 6 月 17 日。由于他们不理解为什么做出某些决定，这些选择看起来就显得武断而不合理。每个人都在挣扎，试图在没有任何确切信息帮助的情况下，对这一模糊的局面形成清晰的认识。每个人看到的项目最终目标都不一样，我们还应该感到惊讶吗？

为了驱散迷雾，你需要与团队分享那些能让他们了解你们共同事业的关键信息。让他们知道，项目需要在 6 月中旬发布，才能比竞争对手的产品早三周上市。帮助他们理解，这个项目满足了公司一项更宏大的国际扩张战略中的某种需要，或者你的客户正指望它来挽回他们现有但日渐老化的产品线不断下滑的利润。

如果你刚开始分享信息，要小心。作为团队的信息渠道，你也会塑造团队的士气。当你决定抱怨另一个小组或经理，或者你团队中的某个成员时，你的消极态度会像流感一样迅速在团队中传播开来。而且，就像病毒感染一样，它会让团队的热情连续几天低落。

分享项目信息的一个好方法是每天开一次会。10 人左右的团队只需 10 到 20 分钟就能有效地开完会。每个人都有一到两分钟的时间向团队通报自己的最新进展，并在需要时寻求帮助。这些快速的“站会”正是软件项目经理分享项目最新情况的理想场合。

如果你选择每周（或每月）开一次会，你可能会忘记重要的信息。毕竟，等到大家终于聚在一起时，这些对你来说已经是旧闻了。或者，一个本可以预防的问题会因为你推迟分享风险指标而爆发。也许在你把 17 条“至关重要”的信息一股脑儿塞进一次冗长的团队讲话之后，团队早已目光呆滞。

记住，你的团队以及公司里的每个人都希望成功。分享你的愿景，也请别人分享他们的愿景。你会发现，你以为一心要让公司关门的那些白痴，大多数其实都是会与你并肩作战、共同解决彼此都理解的团队挑战的人。

=== True_Sucess_Comes_With_A_Supporting_Organization.htm
# 真正的成功来自一个支持性的组织
如果组织回避风险规划、积极发现问题和及时解决问题，原因可能出在文化上。项目团队中那些唱反调的人，常常被贴上麻烦制造者的标签。如果组织动不动就“枪毙报信人”，团队成员就会避免分享棘手的问题，并且可能倾向于隐瞒项目问题。

这种文化环境助长了推卸责任的行为，损害了整个组织、员工个人以及客户的利益。软件项目经理的职责是提供可预测的项目交付，尽可能少地出现意外事件。如果没有人及早指出陷阱，往往就会出现“意外”。这些意外很少是好事，而通常是糟糕的意外，说明由于开发人员隐瞒问题、不让其暴露，预见和规划根本无从谈起。

明智的高管会确保公司支持那些能让开发人员有效工作的态度和行为。这包括评估人力资源政策和激励计划，确保它们与那些能开发出强大产品和服务的行为相一致。

一个典型的不一致的例子是：一个组织在官方层面“宣扬”团队合作，却总是奖励个人贡献。人们很聪明，他们知道哪条路最符合自己的利益。如果高层管理者能让他们所宣称的信念，与他们为鼓励高效行为而提供的工作环境保持一致，那么个人和组织都能蓬勃发展。

如果你发现自己身处一个不提供支持或运转不良的组织中，下面是一些你可以采取的步骤：

1. 不断地问，直到你理解项目的范围，这样你才能在范围之内工作。
2. 找到可能的团队成员和其他干系人。只要有可能，就让他们参与头脑风暴、规划和项目执行。
3. 让那些实际干活的人充分参与项目的更新和决策，至少在他们完成在这个项目上的活动之前都要如此。
4. 始终做一名诚实的软件项目经理。永远不要为了避免冲突或令人不快的讨论而掩饰或简化问题。
5. 在你的项目团队内部营造你希望整个组织都能效仿的环境。

项目经理必须对项目保持客观。他们处在一个吃力不讨好的位置上：首先要效忠于给他们发工资的组织，同时又需要与开发人员建立信任。如果项目前景黯淡，一位精明而有原则的项目经理应该建议取消项目，直到外围问题得到解决。

我们都希望在一个拥有一致战略、支持新软件项目开发的组织中工作。但遗憾的是，即使在同一个组织的不同部门之间，这种能力水平也可能有天壤之别。由于朝着更具支持性的环境迈进对所有人都有好处，因此，提醒高层管理者注意项目优先级与绩效奖励之间的文化冲突，应该成为软件项目经理职责的一部分。

=== Establish_Project_Management_Governance.htm
# 建立项目管理治理
一个项目可能与一个广泛的群体打交道，其中包括团队成员、供应商团队成员、客户或项目发起人、运营团队、合同团队、财务团队以及其他相关干系人。在这种项目涉及大量人员的情况下，各种情境因素都可能危及项目。

如果你是一位来自信息技术（IT）背景的软件项目经理，了解如何融入你所在部门之外更大范围的项目管理视角，可能会对你有所帮助。

治理是一种管理方法，用于制定、传达、实施和监控用于运作项目的政策、程序、实践和其他行为。建立有效的项目治理结构和程序，有助于确保项目保持一致、对威胁和机会进行监控、做出决策，以及交付专注于既定计划的项目工作包。它能让你恰当地应对风险，从而满足项目需求。

为了行之有效，项目治理应该提前规划。在其框架中处理相关事项，例如：治理的目标和目的；结构；原则；流程、程序和标准；沟通；汇报关系；升级程序（什么、何时、如何、由谁）；工具；明确定义并落实的职责和问责；度量以及度量标准；质量；会议和指导委员会；审计；以及监控。

要记住，治理可能会受到一系列因素的影响：环境、领域、行业、公司文化和法律法规。例如，在职能型组织中，作为项目经理的你可能直接向职能经理汇报，而不是向项目组合经理或项目集经理汇报。在项目型组织中，所有工作都以项目的形式开展，项目经理的权力最大。然而，在职能型组织模式中，你可能直接向直线经理或部门经理汇报，这实际上削弱了你的权力。

因此，在规划和定义治理架构时，要考虑组织的层级结构。可以根据工作的演变和进展，按需修改这一结构，以使项目与其计划的目标和目的保持一致。在大型项目中，要让你的工作与更大的项目集或项目组合的目标和目的保持一致。但即使你管理的是一个非常小的项目，也要创建或调整一个项目治理模型。

通常，项目管理办公室（PMO）负责定义和管理与项目相关的程序、流程，并制作应当遵循的模板。

项目委员会是一个负责确保项目目标得以实现的组织机构。它为恰当地应对项目风险以及其他问题提供支持。委员会有以下一些职能：

- 批准项目计划和对计划的变更；
- 收集用于进展报告的信息；
- 确保遵守政策、程序、标准和要求；
- 就风险和问题提供指导；
- 审查项目进展。

当项目与其他公司打交道时，项目治理应与其他组织的治理结构以整合的方式运作。

# 我讨厌你的网站的 9.7 个理由
大多数公司并不知道软件开发和网站开发是不同的，所以软件项目经理和软件开发人员会被要求去做网站。下面是 9.7 种方法，能让你那个烦人的网站使我永远不和你的公司做生意。

1. <b>一开始就放一个加载缓慢的 Flash 画面。</b>不让我跳过它，然后在每个页面刷新时继续让我无休止地等待。你的竞争对手那飞快的响应速度正在召唤我。
2. <b>用令人吃惊、震耳欲聋的视频片段给我“惊喜”。</b>我可能正在上班，可能在家里、身边有熟睡的孩子或配偶，也可能正想买一份惊喜礼物。如果你真想让我离得远远的，那就别提供关闭按钮。
3. <b>禁用“后退”按钮。</b>你阻止我回到把我带到你网站的那个搜索引擎，自以为很聪明，但我不会被困住第二次。下次，我不会再点击你的页面，也不会购买你销售的任何产品或服务。
4. <b>选择一套难以看清的配色方案。</b>在稍深一点的灰色背景上用灰色文字，也许很独特，但根本没法读。鼠标一点，就有 25 个别的网站可以让我不必看瞎眼睛就能读到信息。另外，用反白文字又不让我轻松地剪切和粘贴，意味着我无法保存你的数据，供以后做购买决策时参考。
5. <b>无视我的便携设备。</b>我可能带着 iPhone、Kindle 或上网本。如果你没有一个快速、轻量的移动界面，你就不是我需要的现代化组织。我们正在远离客户端/服务器模式，回到连接着天上某台强大计算机的老式“哑终端”。为此做好准备吧。
6. <b>不提供任何能让我通过电话联系到真人的方式。</b>如果我遇到了问题，在我已经用尽了你们网站支持功能有限的帮助之后，还坚持要我使用它，这实在是不对。我要去找你的竞争对手了。难道你不想知道你的网站什么时候坏了吗？
7. <b>坚持要我打电话才能获取信息。</b>除非你卖的是一种前所未有的产品，比如传送到土星，否则你肯定知道自己的价格。把它给我看。竞争对手可以假扮成客户打电话来问到价格。与此同时，你却失去了我这个真正的客户。
8. <b>区别对待不同类型的客户。</b>如果我是企业，就可以获得较旧的操作系统，那么我也不应该仅仅因为自己是个人，就被迫升级到一个不稳定的系统。如果我在航空公司网站上搜索往返航班时刻，那么当我更想逐段选择多城市航班时，我也希望看到所有相同的航班。
9. <b>提供一个毫无用处的搜索功能。</b>我想搜索的是你网站的内容，而不只是与我搜索的主题相关的公关新闻稿。

9.7 <b>给按钮贴错标签。</b>如果“阅读更多”按钮把我带到一个视频片段，我会很生气。我想浏览你基于文字的信息，而不是坐着看完一整段演示。

<b>别让我讨厌你！</b>
