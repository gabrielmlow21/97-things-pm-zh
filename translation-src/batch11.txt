# 保持弹性，让项目管理更简单
17 世纪著名的武士宫本武藏信奉这样一条原则：“不可偏爱任何一种兵器，也不可执着于任何一个流派。”这条建议放在我们的项目生活里同样适用。我们千万不能太依恋某一条管理原则、某一个软件工具或某一门编程语言，把它当成唯一的兵器。只有灵活地看待手头的资源，让它们能以各种不同的方式排列组合，我们才能为那些化身为项目的客户难题，准备好最佳的应对之道。

从定义项目需求的那一刻起，就要保持开放的心态。如果还没和客户谈，你就已经选好了兵器、定好了作战计划，你怎么能确定这套预先定好的方案就是最好的？

挑兵器之前，先把客户的所有需求看个清楚。客户想用你的新软件解决什么问题？这些问题通常牵涉某些业务逻辑，说明现有资源的特性或功能不够丰富。接着，盘点一下组织里现有的各种条件和系统。巧妙地复用现有环境中的部分系统，能让项目的路走得更短、更顺。

可以利用的企业环境因素五花八门，包括公司现有的设施、设备和软件等基础设施，商业和自有的数据库，编程工具，以及员工的技能。

以资源为导向，分析软件或其他项目交付物要满足的客户需求，会发掘出一些组织里早已存在的底层资源。“我们的用户必须能把 XPP34 <b>呼叫中心系统</b>和我们的<b>公司应收账款系统</b>并排着看。”“你们的产品必须和我们的 4465IL <b>遗留软件</b>合并，或者与之兼容。”

你的工作，是就客户期待的各种最终效果问对问题，并弄清现有的资源/软件或系统要如何与你新写的代码相互配合。用这种以资源为导向的方法，你也许能为客户日后想要的改变打下基础。分析做完，你的软件就开始成形为一组新的资源：它们不仅能解决今天的问题，还能用来完成以后的项目、与未来的软件交互。

等你知道了客户想要什么，也知道了组织里有哪些必须考虑的现有资源，“这时”才能挑出对付这个问题的最佳兵器。实际开发可以先集中在几个关键需求上，先交付它们，赢得客户的信任。满足关键需求所需的模块和服务，应该优先实现。

在软件设计上对新路子保持开放，能让你在需求不断变化的世界里，从容地应对软件项目。这种弹性会让项目管理的挑战变得更简单，而不断打造新的兵器和计划，也会让你每天的工作有趣又充实。

=== The_Web_Points_the_Way_For_Now.htm
# Web 指出了方向——至少现在是这样
有个慈善团体的口号是：“我们站在前人的肩膀上，也为后来者提供肩膀。”这句话对我们这些软件开发人员很有意义。每当一种新的架构、语言或平台声名鹊起，我们往往会感叹：“这就是解决所有编程问题的答案。”它也许能解决今天的问题，可明天又会有新的挑战摆在面前。

目前，我们所知道的软件架构中，恰好只有一种能扩展到几十亿用户，同时在单个组件出故障时依然稳健*：那就是万维网。迄今为止，Web 是人类建造过的规模最大、使用最多、最稳健的信息检索系统。

Web 为什么运作得这么好？大名鼎鼎的 Apache** 项目创始人之一罗伊·菲尔丁（Roy Fielding），研究的正是这个问题。菲尔丁分析了早期 Web 的一个理想化版本的架构，从中提炼出了架构风格的要素。

成果是一种新的软件架构风格，具备我们所钟爱的 Web 的那些特性：面对变化和特定组件的故障都很稳健；关注点相互分离，让我们不必再操心编程语言这类实现细节；用一种共同的“通用语”（即母语不同的人之间用来交流的语言）来交换与语言无关的信息请求；扩展能力极强；无状态。

并不是每个网站都遵循这些指导原则，但很多网站都遵循，Web 整体也遵循。不过，这些只是肩膀而已，新的创新架构会在这之上不断发展。

我们可以从 Web 的成功中学到一些重要的东西。也许最重要的一点是：摩尔定律***让我们如今在系统设计中能够容纳大量的抽象。我们不必再对硬件和软件锱铢必较地追求效率，而可以考虑让系统格外稳定、格外稳健、格外易于扩展、格外灵活。我们也可以接受现有架构的低效，因为我们很清楚，它们只是未来创新的基石。

像 Web 这样的分布式系统很难设计。也许是因为我们每个人都是独立的个体。我们把软件系统当作某个人创造出来的东西，就像我们每个人都以自我为中心看世界一样。不过，Web 的分布式系统已经为我们指明了方向。分布式系统更难构想，因而也更难构建，但值得为之付出努力。

当然，技术会变，想法和方法也会变。菲尔丁所描述的那个简单的 Web，不是如今的 Web，也不会是未来的 Web。Web 未必永远能指明方向。适应新系统的关键，在于现在就把弹性设计进我们的系统。只有这样，我们才能开始构建有生命、会呼吸、能适应的软件系统，随时准备好与新的发现融为一体，为后来者提供肩膀。

- 稳健（Robust）——能很好地应对各种变化（有时是无法预测的变化），把功能的损坏、改变或丧失降到最低。
- Apache 项目——一个开源项目，为现代操作系统开发和维护免费的 Web 服务器软件。
- 摩尔定律（Moore's Law）——描述电脑硬件长期趋势的定律：能以低成本放进集成电路的晶体管数量，呈指数级增长。

=== Who_is_my_customer.htm
# 开发人员讨厌进度报告，经理们却爱它
我在全世界最大的软件公司工作，可以作证：开发人员讨厌进度报告。它让他们每周花好几个小时，写下一些在他们看来显而易见、纯属多余的信息。

可对你这位软件项目经理来说，这些数据能让你更全面地掌握项目进展，然后再向上汇报给高层。平均来说，一位项目经理同时掌管五到七个项目。无论是你，还是你的高层管理团队，都需要你收集并传递这些项目数据。

下面几个小技巧，能让开发人员不那么抗拒提交那份“按你所需频率”提交的进度报告：

- 帮他们明白，为什么这份报告对其他团队成员、或者需要根据团队进度做计划的其他部门很重要。人们会为了帮助同伴而更加卖力。
- 如果项目进展缓慢，要了解团队在忙什么。他们在学新的工具或语言吗？这周有没有碰到意想不到的问题和挑战？汇总进度报告时，加上说明，帮别人读懂这些数字。
- 给予恰当的认可。如果你了解遇到了哪些问题和挑战，就能确保任何重要的成就都不会被进度报告的数字埋没。对那些做出了有益的、计划外贡献的人，送一张附近咖啡店的拿铁券。试试发一封抄送整个部门的“干得漂亮，谢谢你，&lt;名字&gt;”邮件。把这项工作和它在“大局”中的意义直接联系起来。
- 如果你管的开发人员不止一个，就设一个集体奖励。“如果连续一个月，每周五下午 3 点前我都收到你们每个人的进度报告，下一个周五下午大家都放假。”或者，“我会带吃的来，请大家吃顿午饭。”谁也不想当那个害团队拿不到奖励的人。
- 让报告写起来容易些。提供一个模板，或者一个提交进度的电子工具。准备好把其中的措辞改写成人人都看得懂的说法。你的副总裁多半看不懂“lcl check-in to main build lab”（本地提交到主构建实验室），你可以改成“功能里程碑 2 已达成；项目进展正常”。

关键在于，一定要站在对方的角度，看待定期提交进度报告这件事。进度报告很重要，每个人都需要知道发生了什么。高层关心里程碑，业务管理层关心预算。作为项目经理，你的工作是确保每位相关方都了解项目的情况——同时也要明白，并不是每位相关方都能在没有你帮助的情况下，完全看懂正在发生的种种技术细节。

找一个好用的输入工具，并尽可能深入地了解背后的工作内容。你就是那座桥梁，要写出一份能满足所有相关方需要的完整进度报告。

=== You_Are_Not_In_Control.htm
# 你并没有掌控一切
我记得我指导过的一个项目团队。那位项目经理显然很想当控制中心。他似乎近乎偏执地需要参与所有“关键”的决策讨论。他会亲自主导每天的站会，项目回顾会上谁能发言，也只由他一个人说了算。我到的时候，他管的这个团队其实已经磨合得很好了。我饶有兴致地注意到，项目经理在场和不在场时，讨论的质量截然不同。

我和团队里几个人一对一聊过，他们坦言，讨厌项目经理召开的所有会议，只盼着赶紧开完。他们觉得自己的时间被浪费了，因为他们真正的意见不受重视。他们说，自己会讲些项目经理想听的话，好让他赶快进入下一个议题。真有问题需要解决时，他们会去找技术负责人。他更愿意参与开放的讨论，所以解决问题也更有效。

我从这个团队学到的是：装出一副掌控局面的样子，和真正掌控局面，不是一回事。事实上，一味地追求掌控，有时反而适得其反。一支经验丰富、磨合良好的团队，会主动避开一个出于私心想掌控一切的人，尤其是当这种掌控对团队没什么好处的时候。

项目经理了解团队互动和不同的领导风格，会大有裨益。不同的项目、不同的团队，需要不同程度的掌控。像我上面说的那种磨合良好、表现出色的团队，除非看得出过多的掌控对自己有什么帮助，否则往往心生反感。

这种掌控常被视为“瞎掺和”。团队嘴上也许答应了，可离开会议室后的行动，未必完全如你所愿。不过，对一支新组建的团队来说，多一点掌控也许能为团队指明方向，为项目确立更清晰的目标。

出色的项目经理会施加恰到好处的掌控，尊重团队成员为手头项目带来的技能、经验和人脉。他们看得出什么时候多一点掌控能帮团队奔向最终目标，也看得出什么时候同样的掌控会拖团队的后腿。

当一位非 IT 背景的项目经理被派去带软件开发项目时，这一点最为关键。团队往往反感外人干涉他们的工作，可能会看轻项目经理为项目带来的本事。

可项目经理的组织能力、让项目始终契合公司目标的能力，以及维护好高层与客户之间沟通渠道的能力，都能为 IT 团队保驾护航，让他们放手去干。

=== Share_the_Vision.htm
# 分享愿景
你是在和一群笨蛋共事吗？你的团队成员想让公司破产吗？有时感觉像是这样，但通常并非如此。事实是，每个人都想成功，都想为自己的贡献感到自豪，不管他们看上去多么像在搞砸你的项目。他们在做自己认为对的事，只是每个人心目中的“对”各不相同。

作为软件项目经理，你怎样让大家齐心协力？要知道，大多数团队都是在黑暗中摸索。他们不知道这个项目为什么重要，它在公司更大的战略中处于什么位置，也不知道截止日期为什么是 6 月 17 日。由于不明白某些决定为什么会这样做，这些选择就显得随意而不合理。每个人都在苦苦挣扎，想在没有任何确切信息可依的情况下，看清这片迷雾。大家眼中的项目终点各不相同，我们还应该感到意外吗？

要拨开迷雾，你需要和团队分享那些关键信息，让他们了解你们共同的事业。告诉他们，项目要在 6 月中旬发布，才能比竞争对手的产品早三周上市。帮他们明白，这个项目是为了配合公司更大的海外扩张战略，或者你的客户正指望它来挽回现有、却日渐老化的产品线不断缩水的利润。

如果你刚开始学着分享信息，要多加小心。作为团队的信息渠道，你也在左右团队的士气。当你决定抱怨另一个小组、另一位经理，或者团队里的某个人时，你的负面情绪会像流感一样迅速在团队里蔓延开来。而且和病毒感染一样，它可能让团队好几天都提不起精神。

分享项目信息的一个好办法，是每天开一次会。10 人左右的团队，只要 10 到 20 分钟就能开得很有成效。每个人有一两分钟时间，向团队通报自己的最新进展，需要的话请大家帮忙。这种快速的“站会”，正是软件项目经理分享项目最新消息的绝佳场合。

如果你选择每周（或每月）开一次会，可能会忘掉重要的信息。毕竟，等大家终于聚齐时，这些对你来说早已是旧闻了。或者，一个本可避免的问题，因为你迟迟没有分享风险信号而爆发了。又或许，你把 17 条“至关重要”的信息一股脑儿塞进一场冗长臃肿的团队讲话里，大家早就听得两眼发直了。

记住，你的团队，以及公司里的每个人，都想成功。分享你的愿景，也请别人分享他们的。你会发现，那些你以为一心要让公司关门的笨蛋，大多其实是会和你并肩作战、一起解决大家都清楚的团队难题的人。

=== True_Sucess_Comes_With_A_Supporting_Organization.htm
# 真正的成功，来自一个支持你的公司
如果一个组织回避风险规划，不主动寻找问题，也不及时解决问题，原因可能出在文化上。项目团队里那些故意唱反调的人，常常被扣上“麻烦制造者”的帽子。如果组织动不动就“迁怒于报信的人”，团队成员就会避而不谈棘手的问题，甚至可能倾向于把项目问题藏起来。

这样的文化氛围会助长互相推诿的风气，损害整个组织、员工个人和客户。软件项目经理的角色，是让项目交付可预测，尽量减少意外。如果没有人及早指出陷阱，往往就会冒出“惊喜”。这些很少是好的惊喜，多半是难看的那种：开发人员把问题捂着不让暴露，根本不可能事先预见、事先规划。

明智的高层会确保公司支持那些能让开发人员发挥效率的态度和行为。这包括审视人事政策和激励计划，确保它们与能打造出过硬产品和服务的行为相一致。

一个典型的不一致的例子是：组织表面上大力“宣扬”团队合作，却一贯奖励个人贡献。人都很精明，知道哪条路对自己最有利。如果高层能让自己声称信奉的东西，与为鼓励高效行为而提供的工作环境保持一致，个人和组织就都能蓬勃发展。

如果你发现自己身处一个不支持你、或者运转失灵的组织，下面是一些你可以采取的步骤：

1. 不断地问，直到弄清项目的范围，这样你才能在范围之内工作。
2. 找出可能的团队成员和其他相关方。只要条件允许，就让他们参与头脑风暴、规划和项目执行。
3. 让真正干活的人充分参与项目的进展更新和决策，至少在他们完成这个项目上的工作之前都要如此。
4. 始终做一个诚实的软件项目经理。永远不要为了避免冲突或尴尬的讨论，就粉饰问题或把问题简单化。
5. 在你的项目团队里，营造你希望整个组织都能拥有的环境。

项目经理必须客观地看待项目。他们处在一个吃力不讨好的位置：首先要效忠于付他们薪水的组织，同时又要和开发人员建立信任。如果项目前景黯淡，一个精明而有原则的项目经理，应该建议先取消项目，等外围的问题解决了再说。

我们都希望在一个有统一战略、支持新软件项目开发的组织里工作。可惜，即使在同一个组织里，各部门之间在这方面的能力也可能天差地别。既然朝着更具支持性的环境迈进对大家都有好处，提醒高层注意项目优先级与绩效奖励之间的文化冲突，就应该成为软件项目经理职责的一部分。

=== Establish_Project_Management_Governance.htm
# 建立项目管理的治理机制
一个项目可能要和一大群人打交道，包括团队成员、供应商团队成员、客户或项目发起人、运营团队、合同团队、财务团队，以及其他相关方。在这种牵涉众多人员的情况下，各种各样的状况都可能危及项目。

如果你是 IT 出身的软件项目经理，了解怎样融入你部门之外更大范围的项目管理，可能会对你有帮助。

治理（governance）是一种管理方法，用来制定、传达、实施和监控运作项目所需的政策、规程、做法和其他举措。建立有效的项目治理结构和规程，有助于确保项目方向一致、监控威胁和机会、做出决策，以及交付紧扣项目计划的工作包。它能让你恰当地应对风险，从而满足项目需求。

要想有效，项目治理应该提前规划。在治理框架中处理相关事项，例如：治理的目的和目标；结构；原则；流程、规程和标准；沟通；汇报关系；上报规程（报什么、何时报、怎么报、由谁报）；工具；定义清楚并切实落实的职责和问责；衡量方法和衡量标准；质量；会议和指导委员会；审计；以及监控。

要记住，治理可能会受到一系列因素的影响：环境、领域、行业、公司文化和法律法规。比如，在职能型组织里，你作为项目经理，可能直接向职能经理汇报，而不是向项目组合经理或项目群经理汇报。在项目型组织里，所有工作都以项目的形式开展，项目经理的权力最大。但在职能型组织模式下，你可能直接向直线经理或部门经理汇报，权力实际上被削弱了。

所以，规划和定义治理架构时，要考虑组织的层级结构。这个结构可以随着工作的推进和进展按需调整，让项目始终与既定的目的和目标保持一致。在大型项目上，要让你的工作配合更大的项目群或项目组合的目标。但即使你管的是很小的项目，也要建立或调整一套项目治理模式。

通常，项目管理办公室（PMO）负责定义和管理与项目相关的规程和流程，并制定应当遵循的模板。

项目委员会是负责确保项目目标实现的组织机构。它为恰当应对项目风险及其他问题提供支持。委员会的职能包括：

- 批准项目计划及计划变更；
- 收集用于进度汇报的信息；
- 确保遵守政策、规程、标准和要求；
- 就风险和问题提供指导；
- 审查项目进展。

当项目与其他公司打交道时，项目治理应该与其他组织的治理结构融为一体地运作。

# 我讨厌你的网站的 9.7 个理由
大多数公司不知道软件开发和网站开发是两码事，于是软件项目经理和软件开发人员就被叫去做网站。下面这 9.7 招，能让你那个惹人厌的网站，叫我永远不和你的公司做生意。

1. <b>一上来先放一个加载奇慢的 Flash 画面。</b>还不让我跳过，然后每个页面刷新时，都让我接着无休止地等下去。你竞争对手那飞快的响应速度，正在向我招手。
2. <b>用吓人一跳、震耳欲聋的视频给我“惊喜”。</b>我可能在上班，可能在家、身边睡着孩子或另一半，也可能正在偷偷买礼物。如果你真想把我赶走，那就别放关闭按钮。
3. <b>让“返回”按钮失灵。</b>你不让我回到把我带到你网站的搜索引擎，自以为很聪明，可我不会上第二次当。下次，我不会再点你的网页，也不会买你卖的任何产品或服务。
4. <b>选一套很难看清的配色。</b>在稍深一点的灰色背景上用灰色的字，也许很别致，却根本没法读。鼠标一点，就有 25 个别的网站，让我不用看瞎眼睛也能读到信息。此外，用反白的字又不方便我复制粘贴，意味着我没法把你的资料存下来，留作日后的购买参考。
5. <b>无视我的随身设备。</b>我可能带着 iPhone、Kindle 或上网本。如果你没有一个快速、轻量的移动版界面，你就不是我需要的现代企业。我们正在离开客户端/服务器模式，回到老式的“哑终端”，连着天上某台强大的电脑。为此早做准备吧。
6. <b>不给我任何打电话找到真人的途径。</b>如果我遇到问题，在我已经把你们网站支持功能那点有限的帮助都用尽之后，还坚持让我继续用它，这就太不像话了。我这就去找你的竞争对手。难道你不想知道自己的网站什么时候出了毛病吗？
7. <b>非要我打电话才能拿到信息。</b>除非你卖的是前所未有的产品，比如传送到土星，否则你肯定知道自己的价格。给我看看。竞争对手可以冒充客户打电话问到价格，你却失去了我这个真正的客户。
8. <b>对不同类型的客户区别对待。</b>如果我是企业，就能用上较旧的操作系统，那我就不该只因为自己是个人，就被迫升级到一个不稳定的系统。如果我在航空公司网站上查往返航班，那么当我想逐段挑选多城市航班时，也应该看到所有同样的航班。
9. <b>放一个形同虚设的搜索功能。</b>我想搜的是你网站的内容，而不只是和我的搜索主题相关的公关新闻稿。

9.7 <b>把按钮标错。</b>如果“阅读更多”按钮把我带到一段视频，我会很恼火。我想快速浏览你的文字信息，而不是坐着看完一整场演示。

<b>别让我讨厌你！</b>
