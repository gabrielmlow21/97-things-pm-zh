太聪明的代码很难维护

David Wood Fredericksburg, Virginia, USA

开发人员常常被要求创造奇迹。他们得想出巧妙的办法，让今天的项目代码和昨天那些打满补丁的老旧系统一起运作。凭着技术和聪明才智，他们也许能写出一大堆巧妙的代码，最终把事情搞定。可这样的代码又长又复杂，太聪明的代码往往只会给以后的维护埋下麻烦。也许还有更好的办法。

如果你是刚接触软件开发的项目经理，别怕让开发人员去尝试新的语言和开发工具。给他们这份自由，因为他们正是这样找到改进编码方式和成果的新路子的。针对你的旧系统接口问题，他们也许能设计出一个更快的方案，需要测试和维护的代码也更少。这对你的项目当然有好处。

有一些新的编程语言，能用少得多的代码实现和现有语言同样的功能。好处在于：代码结构越简单，就越容易测试、越容易读懂、占的空间越小，也越容易维护。

当然，在公司里引入新的语言和平台，难免会有一些顾虑。这些新代码真能解决现有软件或正在开发的升级版本的问题吗？从长远看，它能不能和旧数据库用的软件、公司内部的用户界面，以及公司已经花钱买的第三方软件接得上？

团队或部门里，还有没有其他开发人员会用这门语言、能在这个平台上开发？语言的作者能不能提供足够的支持？会不会及时更新和改进？

就算你自己不熟悉编程，也别对让程序员拥抱新语言有抵触。如果这门新语言的渊源能追溯到 C 或 Java（或其他常见的做法），把它融进你现有的做法里，大概不会太痛苦。

不过，代码里用到的新做法，一定要记录下来。不然，你的代码和关于代码的文档可能会越走越远，到最后，想了解系统只能直接去读代码。这叫软件组件和系统说明之间“失去了关联”。而一旦文档不足以支撑你维护软件系统，就只能把系统换掉了。

鼓励项目团队的开发人员去创新，但别聪明到过度复杂。太聪明，会让后来的人很难办。如果后来的开发人员读不懂代码，又怎么能指望他们去维护？某个程序员也许想靠卖弄聪明来保住饭碗，但没有哪个项目经理能从中得到好处。

太聪明的代码，最终会变得很难维护，进而导致维护失败，以及代价高昂的软件系统返工。
