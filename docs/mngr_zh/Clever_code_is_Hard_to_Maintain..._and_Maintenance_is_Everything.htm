太聪明的代码很难维护

David Wood Fredericksburg, Virginia, USA

开发人员常被要求创造奇迹。他们要想出巧妙的办法，让今天的项目代码和昨天那些打满补丁的旧系统一起运作。凭着技术和聪明才智，他们可能写出一大堆巧妙的代码，最后把事情搞定。但因为代码又长又复杂，太聪明的代码往往只会给以后的维护带来麻烦。也许还有更好的办法。

如果你是刚接触软件开发的项目经理，不要怕让开发人员去试新的语言和开发工具。给他们这种自由，因为他们正是靠这种方式，找到改进写代码方式和成果的新方法。他们也许能为你的旧系统接口问题设计出更快的方案，而且要测试和维护的代码更少。这对你的项目当然是好事。

有一些新的编程语言，能用少得多的代码做到和现有语言一样的事。好处是：代码结构越简单，越容易测试，越容易看懂，占的空间越小，也越容易维护。

当然，在公司里引入新语言、新平台，也会有一些顾虑。这些新代码真的能解决现有软件或正在开发的升级的问题吗？长期来看，它能不能和旧数据库用的软件、公司内部的用户界面，以及公司已经花钱买的第三方软件接得上？

团队或部门里还有没有其他开发人员会用这种语言、会在这个平台上开发？语言的作者有没有足够的支持？会不会及时更新和改进？

就算你自己不熟悉编程，也不要不愿意让程序员用新语言。如果这门新语言的来历可以追溯到 C 或 Java（或其他常见的做法），把它加进你现有的做法里，大概不会太痛苦。

不过，一定要把代码里用到的新做法记录下来。不然，你的代码和关于代码的文档可能会越差越远，到最后，要了解系统只能直接看代码。这叫软件组件和系统说明之间“失去联系”。而当文档不足以维护你的软件系统时，就只能把它换掉了。

鼓励项目团队的开发人员创新，但不要聪明到过度复杂。太聪明会让后来的人很难办。如果后来的开发人员看不懂代码，又怎么能指望他们去维护？某个程序员也许想靠卖弄聪明来保住饭碗，但没有哪个项目经理会因此受益。

太聪明的代码最终会很难维护。这会导致维护失败，以及代价很高的软件系统返工。
