聪明的代码难以维护

David Wood Fredericksburg, Virginia, USA

开发人员常常被要求创造奇迹。他们必须想出巧妙的办法，让今天的项目代码与昨天那些打满补丁的陈旧遗留软件协同工作。凭借技能和聪明才智，他们也许能写出大量巧妙的代码，最终把活儿干完。但由于代码的长度和复杂性，聪明的代码可能只会给将来的维护制造麻烦。也许还有更好的办法。

如果你是一名刚接触软件开发的项目经理，不要害怕让开发人员去探索新的语言和开发工具。给他们这种自由，因为他们正是通过这种方式，发现改进编码实践和成果的创新方法。他们也许能为你的遗留接口问题设计出一个更快的软件解决方案，而且需要测试和维护的代码行数更少。这对你的项目无疑是一个优势。

有一些创新的新编程语言，可以用少得多的代码行实现与你现有语言相同的功能。其价值在于，更简单的代码结构更容易测试，可以做到自我说明，占用的存储空间更小，也更容易维护。

显然，在组织内部引入新的语言和平台会有一些顾虑。这些新代码真的能解决当前软件或正在开发的升级所面临的问题吗？从长远来看，它能否与遗留数据库所用的现有软件、组织内的用户界面，以及公司已经投资的第三方软件对接？

团队或部门中是否还有其他开发人员能够使用这种语言或在这个平台上开发软件？语言的作者是否提供了足够的产品支持？是否会有及时的更新和改进？

即使你自己并不熟悉编程，也不要不愿意让程序员采用新的语言。如果这门新语言的曲折谱系可以追溯到 C 或 Java（或任何其他常见的做事方式），那么把它融入你现有的实践中可能会相对轻松。

不过，一定要把代码中的任何新做法记录下来。否则，你的代码库和关于代码的文档可能会分道扬镳，以至于了解系统的最佳方式就是直接看代码本身。这被称为软件组件与系统元数据之间的“耦合丢失”。而当文档不足以维护你的软件系统时，就必须替换掉它了。

鼓励你的项目团队开发人员勇于创新，但不要聪明到过度复杂的地步。太过聪明会让后来的人很为难。如果后来的开发人员读不懂代码，又怎么能指望他们去维护呢？某个程序员也许会为了保住饭碗而卖弄聪明，但没有哪个项目经理会从中受益。

过于聪明的代码最终会难以维护。这会导致维护失败，以及对软件系统代价高昂的返工。
