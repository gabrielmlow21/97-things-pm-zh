建立更灵活的沟通方式

Brian Sam-Bodden Scottsdale, Arizona, USA

大多数失败项目的复盘，都把很大一部分责任归咎于软件项目经理、团队成员和相关方之间的沟通中断。项目经理被教导要减少团队成员之间的沟通中断，并持续、有效地沟通。这份责任压在肩上，有时会让项目经理反应过度：他们分不清两种沟通，一种是必要、具体的沟通，另一种是噪音太多、非但无益反而拖慢项目的沟通。

为了解决这个问题，许多软件开发工作正转向更灵活、更敏捷的流程。敏捷方法的关键，是及时的沟通循环，让敏捷团队能有效应对意料之外的变化，迅速重新评估项目功能、重新排定优先级。

敏捷项目经理怎样让沟通只保留必要的部分？他们推行每天的“15 分钟站会”。站会上，开发人员要说明：上次站会以来完成了什么、“今天”打算完成什么，以及预计实现目标时会遇到什么障碍。站会的风险在于，它可能完全依赖每个开发人员自我评估得准不准。怎么解决？为了让站会更有效，可以接入一个能显示功能测试结果的任务管理工具。工具不会对项目代码的状态撒谎，测试结果是对开发人员自我评估的宝贵补充。用报告数据把一个功能和它通过的那组测试对应起来，更能准确地反映这个功能的状态。

比如，持续集成工具的结果，就能客观地描绘出进展。这样，站会的沟通就只剩下必要的内容：报告障碍（但愿任务管理工具已经捕捉到了），以及由边界情况、集成难题和缺陷引发的意外情况。通过一个共享、人人都能访问的工具来呈现开发中的这些“发现”，开发人员能得到更精确的反馈。功能和任务之间不易察觉的关联，也常常能提早被发现。

一个常见的误解是：同步*沟通总比异步**沟通更有效。其实，借助开发工具和简短的异步沟通循环，可以很好地补充面对面的沟通。

在更宏观的反馈层面，Wiki*** 系统能轻松地让项目愿景随着开发进度的实际情况而调整。这样的系统还能及时提供信息，并提供一个更高层次的渠道，与广大相关方沟通——他们未必关心某个功能卡在了哪个深奥的技术细节上。相比之下，软件开发人员对整个项目的看法，可能会被日常技术工作的琐碎细节一点点磨得模糊。Wiki 是让所有参与者对项目保持清晰、一致认识的有效办法。

只要着力让信息循环保持紧凑、没有噪音，软件项目经理就能帮忙避免那种常被视为项目失败元凶的沟通中断。项目经理的责任和挑战，就是精简项目各个层面的反馈循环。

  • 同步沟通（Synchronous Communication）——所有人同时参与，无论是当面还是通过网络。
  • 异步沟通（Asynchronous Communication）——大家都能看到信息，但不必同时在场、实时在线。例如电子邮件、讨论区和共享文件夹。
  • Wiki——一种让用户协作编写网站内容的服务器程序。
