引入更敏捷的沟通体系

Brian Sam-Bodden Scottsdale, Arizona, USA

大多数对失败项目的回顾，都把很大一部分责任归咎于软件项目经理、团队成员和干系人之间的沟通中断。项目经理被教导要减少团队成员之间的沟通中断，并提供持续、有效的沟通。这一责任的分量有时会导致项目经理反应过度。他们模糊了两类沟通之间的界限：一类是必要的、具体的沟通，另一类则是内容与噪声之比实际上阻碍而非帮助项目进展的沟通。

为了解决这个问题，许多软件开发工作正朝着更灵活、更敏捷的流程发展。敏捷方法论的关键在于及时的沟通回路，它使敏捷团队能够有效地应对不可预见的变化，并迅速重新评估项目功能、重新确定其优先级。

敏捷项目经理如何把沟通保持在必要的范围内？他们推行每日的“15 分钟站会”。站会上，开发人员要说明自上次站会以来完成了什么、计划“今天”完成什么，以及他们预见到在实现目标的过程中会遇到哪些障碍。站会的负面风险在于，它可能完全依赖于每个开发人员自我评估的准确性。解决办法是什么？为了让站会更有效，可以集成一个能显示功能测试结果的任务管理工具。工具不会对项目代码库的状态撒谎，测试结果是对开发人员自我评估的宝贵补充。展示把某项功能与它所通过的一组测试关联起来的报告数据，能更准确地反映该功能的状态。

例如，持续集成工具的结果可以客观地描绘出进展情况。这就把站会的沟通压缩到了必要的内容上：报告障碍（希望任务管理工具已经发现了它们），以及由于边界情况、集成挑战和缺陷而出现的意外情况。通过一个共享的、全局可访问的工具来反映这些开发中的“发现”，开发人员能获得更高精度的反馈。功能和任务之间不易察觉的联系，往往也能及早被发现。

一个典型的误解是：同步*沟通总是比异步**沟通更有效。增加开发工具和简短的异步沟通回路，可以有效地补充面对面的沟通。

在更一般的反馈层面上，Wiki*** 系统可以轻松地让项目愿景随着开发进展的实际情况而调整。这样的系统还能及时提供信息，并提供一个更高层面的渠道，与广大干系人沟通，他们可能对阻碍某项功能进展的深层技术细节不感兴趣。相比之下，软件开发人员对整个项目的认识，可能会随着时间的推移被日常技术工作中的琐碎细节所模糊。Wiki 是让所有参与者对项目保持清晰、共同认识的有效方式。

通过着手解决保持信息回路紧凑、无噪声的问题，软件项目经理可以帮助避免那种通常被归咎为项目失败原因的沟通中断。项目经理的责任和挑战，就是精简项目各个层面的反馈回路。

  • 同步沟通（Synchronous Communication）——所有参与者同时参与，无论是当面还是通过虚拟方式。
  • 异步沟通（Asynchronous Communication）——参与者可以获取信息，但不必亲自到场、实时在线。例如电子邮件、讨论板和共享文件夹。
  • Wiki——一种允许用户协作编写网站内容的服务器程序。
