让项目发起人自己写需求

Miyoko Takeya, PMP Tokyo, Japan

项目失败不只是美国公司的问题。几年前，日本一家顶尖 IT 杂志做过调查：如果用质量、成本和交付三项指标来衡量，日本公司做的项目有超过 75% 被认为是失败的。

在日本，和大多数国家一样，这三项指标失败的头号原因几乎都一样：“需求没定义好”。风险最高的是业务分析能力弱的公司。专门谈到软件开发这类技术项目时，成功被委婉地形容为“不太可能”。这说明，要为软件项目找到、识别并定义真正的需求有多难。

正因为这件事很难，很多项目所有者——比如客户、项目发起人（sponsor）或公司高层——都指望项目经理自己去定义和完善需求。他们很少给出指导，也说不清自己需要什么。既然是软件项目，他们自己又不太懂软件开发，就觉得自己不用说明期望。

软件项目经理通常既没有权力，也没有时间独自去寻找、筛选需求并排定优先顺序。何况项目可能牵涉好几个利益群体，他们对软件做好后该做什么，想法很可能互相冲突。

项目经理需要在项目开始前，花时间和出钱的人坐下来，帮他们说清楚到底想要什么。是做得快更重要，缺陷少更重要，还是花钱少更重要？你不可能样样都要。要做出他们想要的软件，哪些资源和技能是关键的？他们有没有把这些提供给团队？

这个软件会怎样用来支撑公司的运作，或者帮公司赚钱？时间限制是真的吗——比如写进了客户合同、和某个重要节日挂钩，或者是某个大型营销计划的一部分？

如果在定义需求的阶段，没有认真、具体地想清楚这个项目要做出什么，项目就很可能失败。记住，他们要说清楚的是希望软件做什么，而不是程序员要怎么做出来。

要说服项目所有者：他们必须从头到尾参与。扎实的需求规划，能把商业理由、项目目标和项目成果清楚地连在一起。不然，项目就做不出他们期望的结果。

软件项目失败，最受伤的是项目所有者，因为钱是他们出的，他们本来指望靠这个软件把投资赚回来。
