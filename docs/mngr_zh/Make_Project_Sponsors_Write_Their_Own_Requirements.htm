让项目发起人自己写需求

Miyoko Takeya, PMP Tokyo, Japan

项目失败并不只是美国公司的问题。几年前，日本一家顶尖 IT 杂志做过一项调查：以质量、成本、交付三项指标衡量，日本企业的项目有超过 75% 被认为是失败的。

和大多数国家一样，在日本，这三项指标失败的头号原因几乎是同一个：“需求定义不清”。业务分析能力薄弱的公司，风险最大。而专门说到软件开发这类技术项目时，报告对成功的评价委婉得很——“不大可能”。可见，要为软件项目发掘、识别并定义真正的需求，有多难。

正因为难，很多项目所有者——客户、项目发起人（sponsor）或公司高层——就指望项目经理自己把软件需求定下来、理清楚。他们很少给出指导，也说不清自己到底需要什么。在他们看来，这是软件项目，自己又未必懂软件开发，那就用不着交代期望了。

可软件项目经理通常既没有权限，也没有时间，独自去发掘需求、取舍需求、排定优先级。何况项目往往牵涉好几个利益群体，大家对软件做成后该干什么，想法很可能互相打架。

所以，项目经理要在项目启动前，花时间和出钱的人坐下来，帮他们把到底想要什么说清楚。是做得快更重要，bug 少更重要，还是花钱少更重要？鱼与熊掌不可兼得。要做出他们想要的软件，哪些资源和技能必不可少？他们有没有把这些交给团队？

这个软件会怎样支撑公司的日常运转，或者帮公司赚钱？时间限制是不是硬性的——比如写进了客户合同、要赶某个重要节日，或者是某个大型营销计划的一环？

如果在需求定义阶段，没有认真、具体地想清楚这个项目要做出什么，项目成功的希望就十分渺茫。记住，他们要讲清楚的是希望软件做什么，而不是程序员该怎么实现。

要说服项目所有者从头到尾参与其中。扎实的需求规划，能把商业论证、项目目标和项目成果清清楚楚地串起来；否则，项目就交不出他们期待的结果。

软件项目一旦失败，受伤最重的是项目所有者——钱是他们出的，他们本来还指望靠这个软件收回投资。
